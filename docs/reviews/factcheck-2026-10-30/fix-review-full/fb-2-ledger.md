## Method and access limits

- Attempted curl.exe -L -A Mozilla/5.0 into the requested directory. HTTPS curl consistently failed before fetching with Schannel SEC_E_NO_CREDENTIALS. Used Python urllib with the same User-Agent as a fallback, preserving independent fresh downloads. The original Mostek HTTP link redirects to HTTPS; both www and non-www Bitsavers returned HTTP403 in urllib, so web search located the identical named book on deramp.com.
- Ran pdftotext -layout on downloaded PDFs; scanned pages produced little/no usable text. Rendered at 110 dpi with pdftoppm -f N -l N -r 110 -png and visually inspected full pages.
- Visually read MSX printed pp.10,11,14-17,32-34,43-44 (PDF13,14,17-20,35-37,46-47), Motorola MC6809E p.1, AY Fig.4 p.10, Zilog p.5/PDF19, TI pp.3-9/3-10 (PDF52-53), Intel p.6-166/PDF696, Mostek V-33/V-34 (PDF98-99).
- Opened all six distinct HERO cited page URLs (97,99,101,102,103,104), downloaded metadata and BookReader JSON. Every relevant page has viewable:false. Direct source PDF returns HTTP401; encrypted derivative request returned HTTP500. Web searches for the exact book/title and connector tables did not locate a readable primary copy. No access restrictions were bypassed. Consequently there is no basis to certify any of these 174 underlying pin claims.
- Evaluated current data files and git-show HEAD versions in separate Node VM contexts with an RCS.add collector. Compared every scoped connector pin individually, not a text grep. All 174 HERO pin records are exactly identical to HEAD, including all flags and five scoped conflict strings. MSX cassette pin6 on both models also already has its flag in HEAD. Captures: current.json, baseline.json, flag-audit.json and raw *.diff.
- Executed the actual printCard function in a Node VM: removing every verify flag recursively produces byte-identical HTML, with zero Check markers. Saved msx1-printcard.html, print-proof.js and print-proof.json. Presentation/data-access dependencies are documented in the proof; no browser or hardware was exercised.
- Renderer inspection: src/app.js viewPower renders rails without r.verify; printCard renders rails, first-ten checks, clock rows, and connector pin names without their verify flags. On-screen firstTenBlock, clocksBlock and connector legends do use verify. The print-path discrepancy is material for the newly flagged MSX instructions.

## Findings

1. **HIGH - wrong power pin introduced, blocks commit.** src/data/tandy.js:380 / Additional fb-2: MC6809E pin7 is VCC, not GND. Motorola p.1 PIN ASSIGNMENT labels it VCC; pin1 is VSS. Restore the former +5 V supply classification. A ground lead here shorts the supply; this shared chip record affects CoCo1/2/3 and Dragon32/64. Existing +4.9 to +5.2 V probe hint now contradicts the changed name/type/description. Principle: prove-it-works; fix-root-causes (shared chip record).
2. **MEDIUM - verification qualifiers disappear on the repair print card.** Newly flagged MSX CPU-clock and diagnostic rows (15:201/202/208/211/212) are printed by printCard without verify. The rail branch in viewPower also ignores the existing -5 V flag (15:206). Thus a data flag alone does not make uncertainty visible in every repair view. Preserve Check markers through the render paths or replace unresolved instructions with explicit uncertainty in displayed text. Principle: prove-it-works; fix-root-causes.
3. **LOW - fix ledger claims flag additions that are absent from the actual diff.** All 174 scoped HERO pin records (15:27-15:200) are exact no-ops, already flagged in HEAD; the two cassette REMOTE+ pin records and -5 V rail flag were already flagged as well. Five scoped HERO conflict strings also already existed. Correct the old/new accounting rather than crediting these as new repairs. The HERO book is restricted, leaving all 174 claims unproven in this independent review. Principle: prove-it-works.

serialize-shared-state-mutations: no scoped concurrency mutation or ordering change was found. This is a data-only audit; no writes to the shared application state were made.
